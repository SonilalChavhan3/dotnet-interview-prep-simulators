📂 Three Major Categories

State management is not simply "client-side vs server-side."

A. Request / MVC View State

  • ViewData
  • ViewBag
  • TempData
  • ModelState

Tied to the MVC request/response lifecycle. Not strictly client or server.

B. Client-Side State

  • Cookies
  • Query String
  • Hidden Fields
  • LocalStorage
  • SessionStorage

Can be inspected or modified by the user.

C. Server-Side / Persistent

  • Session
  • IMemoryCache
  • Distributed Cache / Redis
  • Claims
  • Database

Temp server state, cache, auth, persistent data.

🔀 Redirect Simulator

Why ViewData/ViewBag do not survive redirects, but TempData does.

▶ Request 1: POST /Product/Create
↓ Controller sets TempData["Success"]
↓ Return RedirectToAction("Index")
↓ HTTP 302 Response sent to browser
▶ Request 2: GET /Product/Index
↓ TempData["Success"] read
↓ View renders message

Key point: ViewData and ViewBag only live for the current request. When a redirect happens, the first request ends and those values are lost. TempData is specifically designed to survive exactly one redirect. 

// Request 1
TempData["SuccessMessage"] = "Product saved!";
return RedirectToAction("Index");

// Request 2
@if (TempData["SuccessMessage"] != null)
{
    <div class="alert">@TempData["SuccessMessage"]</div>
}

🍪 Cookie + Session Relationship

ASP.NET Core

Session Store

Session data is stored server-side. The browser only stores a small session identifier cookie that links the request to the correct server-side session. The browser does NOT store the complete session object.

🖥️ Single Server vs Multi-Server

With a single server, local memory and session work fine.

            ┌── Server 1
Browser → Load Balancer ├── Server 2
            └── Server 3
                    ↓
            Shared Redis

Local memory (IMemoryCache) is not shared between servers. Use a distributed cache like Redis.

Sticky sessions: LB routes the same user to the same server.
Distributed session: Session data is stored in a shared cache.
Redis: Shared in-memory data store used as distributed cache.
Stateless architecture: Servers don't store client state.
Horizontal scaling: Adding more servers to handle load.

🔒 Security Simulator

Client-side state is input. Validate important values on the server.

❌ Bad Practice

var price = Request.Query["price"];

Do NOT trust this price directly.

✅ Better Practice

var product = await _db.Products.FindAsync(productId);
var price = product.Price;

Business-critical values should come from a trusted server-side source.

🍪 Cookie Security Options

new CookieOptions
{
    HttpOnly = true,
    Secure = true,
    SameSite = SameSiteMode.Lax
}
HttpOnly: JavaScript cannot normally access the cookie.
Secure: Cookie is sent only over HTTPS.
SameSite: Controls when cookies are sent in cross-site situations.

These settings reduce risk but do not make an application automatically secure.

🚫 Don't Do This

Don't store passwords in: Cookies, LocalStorage, SessionStorage, Hidden fields, Query strings.

Don't trust: Hidden fields, Query strings, Cookies, LocalStorage, Client-provided prices, Client-provided roles.

Don't use Session for: Permanent business data, Large datasets, Data that belongs in a database.

Don't use IMemoryCache as: A permanent database, A reliable cross-server data store.
